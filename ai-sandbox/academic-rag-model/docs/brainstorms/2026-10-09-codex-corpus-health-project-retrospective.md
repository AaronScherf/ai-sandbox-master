# Codex on a new pipeline: brainstorm, plan, and execution

**Date:** 2026-10-09

**Scope:** Evaluation of Codex's work on the Academic Hub corpus-health orchestrator, from the first design dry run through the installed discovery-only trial. The trial's daily results are pending; this is not a final reliability assessment.

## Brainstorm and design

The first Codex plan got the safety structure right: discover, ask a human to review, apply only selected repairs, verify outcomes, keep Git changes diagnostic, and avoid treating a broad index rebuild or cloud conversion as a cheap per-file action. It also recognized the nested notes checkout and that a scheduled run with no agent could not assume consent. Those were useful first-pass judgments.

Claude's [first review](2026-10-07-corpus-orchestrator-codex-plan-review.md) found six substantive gaps. Codex had missed the project's existing interactive-review convention and adjacent tools (`tools/active_work.py`, `tools/git_workflow.py`, `tools/reconcile_needs_manual.py`); left the no-agent daily mechanism as an open question; specified only dated reports rather than a durable decision ledger; deferred an exact discovery-versus-mutation inventory; and gave no daily scan cost model. Some questions repeated choices already settled by the user's request or repository rules. The root pattern was shallow project-context discovery despite sound general reasoning.

Codex's revised [design](../superpowers/specs/academic_hub/2026-10-07-corpus-health-orchestrator-design.md) closed those points with a capability inventory, cheap discovery, stable finding state, Windows Task Scheduler, and explicit repository boundaries. It correctly replaced the Claude-hosted Artifact convention with a local loopback review page after the user clarified that review must work without an agent. Claude's second review found three residual issues: a lock only held by the orchestrator would not coordinate direct pipeline writers, known device-local notes-sync files would create Git noise, and the design needed to say that a simple read-only scanner was valuable before the server/ledger/repair system existed. These were folded into the [implementation plan](../superpowers/plans/academic_hub/2026-10-08-corpus-health-orchestrator.md). Claude assessed the correction process as strong but did not conclude that one successful, reviewed exercise justified changing the default architecture-routing rule.

## Planning and execution

The implementation plan separated eight tasks and made the scanner independently shippable. Codex completed the scanner, state, local review page, shared writer coordination, one exact-card chunk apply adapter, and the Windows discovery runner. It kept broad card reconciliation, note repairs, and cloud textbook conversion blocked when their exact-scope, quality, cost, or sync gates were unmet. The scheduled trial and reminder were installed only after the user approved that operating mode.

Review improved the implementation materially. A five-issue review of Tasks 1-5 exposed inconsistent textbook-directory matching, a full scan on every review click, missing concurrent-writer and vanished-source tests, and an unresolved rename-versus-identical-duplicate decision. Later live finding inspection exposed textbook identity matching, generated-file exclusions, and frontmatter-reading errors that fixture tests had not caught. The first apply-adapter decision required exact `file_id` selection, structured target-level CLI output, a current-card precondition, explicit blocked/failed/applied ledger states, and atomic index writes. Codex caught a further mismatch between an initially proposed in-process adapter and the plan's required subprocess boundary; Claude revised the decision to require the CLI. These are examples of productive review, not evidence that the initial implementations were already field-proven.

The full tests passed at the final Task 7 and Task 8 gates, and four read-only live scans completed with zero scan errors. A single manual Task Scheduler launch passed. Those results support starting the daily trial, not declaring the corpus healthy or the full repair workflow complete. The seven-day reports and a manual sample of findings still need assessment after October 16. The [implementation handoff](../status/academic_hub/2026-10-09-corpus-health-implementation-retrospective.md) records the remaining adapter and operational limits.

## Instructions added during this exercise

The root [`AGENTS.md`](../../../../AGENTS.md) now tells Codex, when explicitly asked to plan or design, to: search named project locations and existing conventions before proposing architecture; extract requirements and avoid re-asking settled questions; inventory each pipeline's discovery, scope, side effects/cost, outputs, idempotency, and verification; design unattended execution, state, retry, and human review together; define stable finding identity and decision transitions; map real Git repositories and write destinations; and state when extra infrastructure exceeds the minimal useful version. It also now requires a completed-work/status/verification summary after long tasks and a concise next-step question. These rules directly address Claude's first and second reviews. They supplement, rather than silently replace, the repository's default routing of new architecture decisions to Claude; the user explicitly assigned this dry run to Codex.

## Suggested further rules (not yet added to `AGENTS.md`)

1. **Trace a plan through delivery.** Before implementation, map each requirement to a task, acceptance evidence, and a blocked/deferred state. After each milestone, update the plan's status and name what is implemented, merely tested on fixtures, manually observed, or still unverified. This would have prevented the plan's Task 7/8 status from becoming stale after landing and installation.
2. **Treat a repair adapter as an evidence contract.** Require an exact target selector, target-scoped machine-readable result, shared writer coverage for every destination, atomic output where interruption could corrupt state, and a post-run audit before enabling an action. The first adapter review found each of these assumptions mattered.
3. **Field-check classification before trusting counts.** For a scanner or migration, compare a small, diverse sample of live read-only findings against the underlying files/records and document false positives before calling the policy complete. Passing fixture tests did not reveal the textbook, generated-file, and frontmatter mismatches.
4. **Do a proportionality pass after incorporating review.** Re-read the user's original request, identify the smallest usable release, and distinguish required gates from later infrastructure before finalizing a revised design. Addressing every review point can otherwise enlarge the design without clarifying the first useful outcome.

These are recommendations for a later instruction edit, not new authorization to enable note, cloud, or unattended repair actions. The trial review should also inform whether any of them need more precise wording.
