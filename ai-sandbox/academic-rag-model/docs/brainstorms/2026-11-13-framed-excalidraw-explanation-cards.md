# Framed Excalidraw explanation cards — provisional pipeline brainstorm (2026-11-13)

**Status:** Candidate for Claude review, not an approved specification or implementation plan. This document explores a path that could turn the owner's working interactive Gemini procedure into repeatable, eventually unattended, frame-by-frame generation. Read the [Claude handoff](../status/transcribe_notes/2026-11-13-framed-excalidraw-explainer-claude-handoff.md) first. The unknowns there are release gates, not details to guess during implementation.

## Requirements and constraints

1. Input is one exact `.excalidraw.md` scene in the nested `academic_notes` repository, its linked slide PNG assets, an existing frame set, and the optional verified `<scene>.slide-order.json` sidecar. The caller chooses the scene and frame range; never scan the entire vault by default.
2. Use the slide **and visually associated handwriting** for each frame. A frame may contain zero, one, or many ink regions. Show both together to the model without requiring separate handwriting transcription. Reject absent, ambiguous, or obviously clipped ink rather than silently explaining only the slide.
3. Produce exactly **one two-paragraph Markdown card per eligible frame**. The first paragraph explains the concept and its motivation; the second connects equations, the visible handwritten annotations, and interpretation. Use LaTeX only where grounded in the frame. If two paragraphs cannot explain a dense proof honestly, mark `needs_review` and ask Claude whether a separate longer-card mode belongs in a later release.
4. Keep notation and narrative consistent across 5–10 sequential frames by supplying a compact accepted context summary, while identifying every result by its own frame and source slide. PDF page order is by verified slide number, not physical canvas x/y position. Do not move existing slide or ink elements.
5. Prefer account-based subscription Gemini in Antigravity. Keep metered API and local Ollama as explicit opt-in alternatives after separate cost/quality checks. Record which provider actually ran; never silently switch to API-key billing or credits.
6. Place a rendered Markdown-image element beside its slide **inside its associated frame**, preserving all existing elements and prior manual explanations. If no collision-free space or valid frame update exists, produce `placement_conflict`, with no scene mutation for that target.
7. Reruns do not duplicate cards. Changed slide pixels, ink, frame association, prompt version, or user edits trigger a deliberate update/review path. One writer owns the exact scene during apply; precondition hashes, atomic output, recovery copy, and post-run audit are required.

## Candidate flow

### 1. Collect a bounded, auditable frame batch

Run `collect --scene <exact path> --frames <IDs or verified page range> --driver agent` from `pipelines/transcribe_notes/`, adapting the established task-card style. Parse the scene and list for each frame: frame ID/name/bounds, linked slide element ID and asset path/hash, explanation/image elements, assigned `freedraw` IDs and bounds, page number with sidecar evidence, and any clipped or shared ink. `frameId` membership is useful evidence; spatial overlap and the auto-framer's ink warning are independent checks. A frame is eligible only when the slide association is unique and the visual crop contains the ink to be explained. The collector records `eligible`, `ambiguous_match`, `missing_asset`, `clipped_ink`, `existing_card`, or `needs_review` per target. Compare a varied read-only live sample to the underlying scene before trusting aggregate eligibility counts.

The safest known visual bridge is a **user-exported frame PDF** from Printable Layout Wizard, followed by local page-to-PNG rasterization (PyMuPDF is already in the Python environment). This PDF path has scratch evidence for ink visibility, but the page-to-frame mapping still needs explicit proof from names/order and page count. A scriptable direct per-frame SVG/PNG export may remove the manual PDF prerequisite later; verify the installed plugin API before promising it. Passing the original slide PNG alone is insufficient when handwritten strokes are on the scene.

Store the task manifest, rasters, prompt, and output under a scene-scoped `.agent_work/<run-id>/` path, following package conventions. Avoid embedding the whole raw note or unrelated vault files in a prompt. For each batch, include only selected frame images, a short approved notation summary from preceding cards, neighboring slide titles/page labels, and the frame-specific evidence map. No separate OCR/transcription pass is needed for the first release; it becomes useful only if reusable transcripts are wanted elsewhere.

### 2. Generate structured cards through a verified subscription surface

**Interactive first path:** the existing Antigravity IDE agent reads the staged 5–10 frame rasters and writes schema-shaped results into `.agent_work/`; a deterministic `submit` validates them. This is a reproducible collect/submit process but still needs a human to start the agent.

**Headless candidate:** after a no-write feasibility probe, invoke an installed account-authenticated `agy -p` per batch, with `--output-format json` and a schema for an array of frame results. The [CLI documentation](https://antigravity.google/docs/cli/headless/) specifies machine-readable output, schema enforcement, exit status, cached credentials, and noninteractive permission behavior. The model should have read-only access to the staged inputs and no permission to edit the vault; deterministic code owns apply. Do not use `--dangerously-skip-permissions`. Check the JSON `status`, per-frame IDs, paragraph count, grounded notation, empty/duplicate results, and stderr permission notices; an exit code of zero alone does not prove every requested tool succeeded. Pin the model and account route once tested. An API-key provider is an explicit `--driver api` run, with a cost estimate and owner approval where required.

Prompt skeleton: “For each named frame, inspect its visual artifact. Use the slide text and nearby handwriting, distinguishing what is visible from inference. Return exactly two coherent Markdown paragraphs per frame, keyed by frame ID and slide ID. Paragraph 1 gives conceptual intuition; paragraph 2 derives or interprets the visible formulae and annotations. Preserve symbols across the batch. No invented equations, no ungrounded page references, no file edits. If the proof is too dense, the ink is unreadable, or the frame appears incomplete, return `needs_review` with reason instead of compressing away essential steps.” Claude should decide the exact card-length and mathematics thresholds after seeing rendered examples.

### 3. Validate, place, and audit one scene revision

Validate every result against its task manifest and source hashes, then render candidate Markdown cards locally to measure dimensions before writing. Target the frame's free horizontal space using current bounds, not the recovered 2SLS absolute grid. Preserve a practical gap from slide and ink; align the card to the associated slide; keep the whole card in frame bounds. If no valid slot exists, report `placement_conflict` and leave that frame untouched. If enlarging a frame is necessary, require the same foreign-image, neighboring-frame, and ink containment checks as the framer; never move source elements in this pipeline.

To insert, the applier must reproduce the installed Excalidraw plugin's actual Markdown-image contract: marker under `# Markdown Images`, corresponding entry under `## Embedded Files`, correct SHA-1 and `fileId` linkage, and an image element with stable `frameId`. The prior spec explicitly leaves the hash input and ID relationship unverified. Establish the contract from a plugin-created card and an add/reopen/resave/export scratch test before allowing direct scene writes. An in-vault EA insertion route is an alternative for Claude to assess if it provides safer supported APIs. Either route must check the saved file revision, coordinate the sole writer with Obsidian and Git sync, write atomically or through a verified plugin save, keep a recoverable backup, reparse all sections, assert original IDs remain, and audit new card linkage and frame inclusion. Do not run the existing framer blindly after insertion if it would classify the new card as a competing explanation image.

### 4. Stable identity, state, and unattended behavior

Use a frame-task identity based on stable scene-relative namespace + frame ID + slide element ID. Derive an input fingerprint from slide asset bytes, ordered ink element IDs and versions/geometry, frame association, prompt version, and relevant accepted context version. A pure frame resize should not change the prose fingerprint unless visual content or association changes. Store `pending → generated → validated → applied → verified` with terminal `needs_review`, `placement_conflict`, and `declined` states. A repeated identical fingerprint at `verified` is `noop`; a changed fingerprint marks the old result `stale` and creates one new revision of the same logical card, never a second visible card. A declined version stays suppressed on identical input; material changes may reopen it for review. Existing manually written cards are protected unless explicitly selected for adoption or replacement.

For eventual unattended execution, a local scheduled task or explicit CLI invocation scans **only named scenes**, hashes only selected frames, and runs `collect → agy → submit → apply → audit` under an exact-scene lock. The run manifest is machine state, not a human decision page. Retry model/network failures a bounded number of times with backoff using the same immutable task fingerprint; do not reapply a card after an uncertain save until the post-run scene audit resolves its state. If auth expires, quota runs out, the visual tool is denied, Obsidian changes the scene, or no human is present for ambiguity, stop that target with a machine-readable reason and leave the scene intact. A technical status report can list such targets; if the user must decide a match or replacement, provide the workspace's interactive Artifact review surface before accepting a decision. No server or database is necessary to try a single scratch scene; scheduling and whole-vault discovery are later scope.

## Smallest useful release and acceptance evidence

**Candidate first release:** one explicitly selected scratch scene with two or three already framed, unambiguous slides; manually export their PDF; collect and rasterize those pages; let the existing subscription IDE agent produce two-paragraph JSON card results; validate and apply to a scratch copy; reopen in Obsidian and export PDF; rerun and prove no duplicate cards. This delivers end-to-end frame-card value before CLI installation, direct frame export, unattended scheduling, a server, or a database. If the headless image probe passes, it can replace the interactive generation step without changing card identity or apply semantics. Claude should revisit this minimum after its review.

Acceptance should include: varied read-only frame/ink classification with false-positive log; exact page-to-frame mapping; one card per selected frame and no unselected changes; visible slide and ink used in text; plugin-created hash/link contract reproduced; all original scene IDs preserved; correct frame membership; save/reopen/resave/PDF legibility; second run `noop`; changed ink or PNG yields `stale` rather than duplication; ambiguous match, clipped ink, denied agent tool, and scene revision race each yield a specific no-write result. Fixture tests can cover serialization, placement, identity, and retries. Only a live scratch run can establish Obsidian rendering and PDF behavior; neither counts as whole-deck reliability.
