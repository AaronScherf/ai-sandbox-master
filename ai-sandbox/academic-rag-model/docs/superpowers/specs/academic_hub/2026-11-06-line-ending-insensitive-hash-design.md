# Line-ending-insensitive content hash: design and plan

**Status:** design and plan, 2026-11-06. No code changed. Awaiting the owner's go-ahead before any implementation (same gate as the hub path resilience P4 plan).
**Owner of the decision:** Aaron. Implementer: Claude or Codex per `docs/AGENT_ROUTING.md`.
**Related:** `docs/superpowers/plans/academic_hub/2026-11-03-hub-path-resilience-p1-stable-hashes.md` (the precedent: location-insensitive hash, dual-scheme matching, `tools/rehash_content_hashes.py`).

## Problem

`compute_content_hash` (`core/indexer/index_card.py`) hashes a note's raw bytes after dropping location and identity frontmatter lines. It deliberately leaves line endings alone ("every other byte (BOM, CRLF, body) untouched"). The same text with LF endings and with CRLF endings therefore hashes differently (measured 2026-11-06: `e60eac06...` vs `e22ab362...` for one fixture note).

Anything that flips a note's line endings marks its card stale, and a stale card is regenerated by `rebuild` with a paid Gemini call, and its chunks are re-embedded. Sources of flips, all observed in this repo:

- `academic_notes` stores a mix (596 CRLF and 140 LF markdown blobs; `core.autocrlf=false`, no `.gitattributes`), written by Obsidian, Python and the tablet.
- The Obsidian tablet sync and Direct Git Sync rewrite files on a different OS.
- A Python text-mode write on Windows emits CRLF.
- The 2026-11-06 handoff found about 208 `academic_notes` files modified with line-ending-only differences (content identical).

Normalizing the `academic_notes` blobs (adding a `.gitattributes`) is blocked until this is fixed, because it would flip hundreds of files at once.

## Goal and non-goals

Goal: the same note content hashes identically regardless of LF, CRLF or mixed endings, with no mass re-index of existing cards.

Non-goals: changing any note's bytes on disk; normalizing the `academic_notes` repo (a separate owner-run step after this lands); changing identity (`file_id`, `hub_id`) or the location-field exclusion.

## Design

### Scheme

Add a third hash scheme and keep the two existing ones readable.

| Scheme | Definition | Stored by |
|---|---|---|
| legacy | sha256 of raw file bytes | cards before P1 |
| current | sha256 of bytes after `strip_location_lines`, endings preserved | cards since P1 |
| **eol-normalized (new)** | `current`, computed after replacing every `\r\n` with `\n` | cards written after this change |

Normalization replaces CRLF only. A lone `\r` is left alone (not a line ending in any file this repo writes). Truncation to 16 hex characters is unchanged.

`compute_content_hash` becomes the eol-normalized scheme, so every producer that stores a hash starts writing it with no call-site change.

### Matching (the part that avoids a mass re-index)

`content_hash_matches(md_path, stored)` accepts `stored` if it equals any of: new, current, or legacy, each computed over every line-ending variant of the file's bytes (as-is, all-LF, all-CRLF). That covers a card written under CRLF whose file is now LF (or the reverse) under either old scheme, as well as new-scheme cards. Cost: at most 3 variants times 3 schemes of SHA-256 over one file, no I/O beyond the existing single read.

Consequence: merging this code makes no existing card stale and requires no migration to be safe. A migration is an optimization (below).

### Direct comparisons

Two call sites compare `compute_content_hash(path)` to a stored value with `==`, bypassing `content_hash_matches`. After the scheme change each would call every existing card changed, so they must move to `content_hash_matches`:

- `core/indexer/markdown_sources.py:83` (stored value from a plan row or card)
- `core/indexer/reconcile_apply.py:469` (copy check against `want`)

`core/indexer/markdown_sources.py:189` compares two files' hashes (duplicate detection); under the new scheme it becomes line-ending-insensitive, which is the desired behavior, and needs a test only.

The remaining modules that import the hash functions (about 19; list in Task 3) are classified as: stores a new hash (fine), compares to a stored hash through `content_hash_matches` (fine), or compares directly (fix). Task 3 produces that table before any edit.

### Chunk records

Chunk records carry the card's hash and must equal it, or the chunks look stale and are re-embedded (`chunk_index.py` lines 366 and 459 compare `c["content_hash"] == card["content_hash"]`). The invariant is preserved by never rewriting a card hash without rewriting its chunk records in the same operation, exactly as `tools/rehash_content_hashes.py` already does. Chunks of a card whose hash is unchanged are unaffected.

### Migration (optional optimization)

Extend `tools/rehash_content_hashes.py`: when a card's stored hash matches the file under any accepted scheme and variant, rewrite the card hash and its chunk hashes to the new scheme. Dry run by default, `--apply` under the corpus write lock, no network. Not required for correctness; it makes later comparisons cheaper and stops cards from depending on the compatibility path. Run it only when the hub is quiet.

### Rollout and the multi-agent hazard

Other worktrees may run `rebuild` with older code. Once cards carry the new hash, older code (which computes the current scheme) would call them stale and regenerate them at paid cost. Mitigations: land this change before running the migration; do not run the migration while other branches that touch the indexer are active (`python -m tools.active_work`); announce the change in the status doc so Gemini/Codex sessions rebase first. Matching alone (no migration) is safe even for stale branches because new cards are only written by code that already contains this change.

## Tasks

Each task is test-first, makes zero API calls, and is committed separately on a `claude/` branch.

### Task 1: Characterization tests

Files: `tests/core/indexer/test_content_hash_eol.py` (new).
Pin today's behavior and the target: LF vs CRLF vs mixed vs BOM vs frontmatter-only-hub_id files; legacy and current hashes differ across a flip today (documents the bug); a `strip_location_lines` + CRLF fixture. These tests fail or xfail against the target until Task 2.

### Task 2: New scheme and tolerant matching

Files: `core/indexer/index_card.py`, tests above.
Add `_normalize_eol`, make `compute_content_hash` the eol-normalized scheme, extend `content_hash_matches` with the variant search over all three schemes, keep `compute_legacy_content_hash` and add `compute_current_content_hash` for the middle scheme. Acceptance: for each of {legacy, current, new} stored under LF content, `content_hash_matches` is true for the file in LF, CRLF and mixed form; a one-character content change is false in every form.

### Task 3: Direct comparisons and caller audit

Files: `core/indexer/markdown_sources.py`, `core/indexer/reconcile_apply.py`, plus tests for the callers (`CLAUDE.md` requires caller tests for `core/indexer`).
Produce the table of every module importing the hash functions (store / compare-via-matches / compare-direct / compare-two-files) in this doc's appendix, then fix the direct sites. Acceptance: a fixture hub with cards written under the old scheme and CRLF files converted to LF yields `rebuild_plan` with zero `refresh` rows and `markdown_preview` with zero changed rows.

### Task 4: Migration tool

Files: `tools/rehash_content_hashes.py`, `tests/tools/test_rehash_content_hashes.py`.
Match under any scheme/variant; rewrite card and chunk hashes together; dry run reports counts of rewrite, already-new, stale (genuinely changed), missing. Acceptance: chunks of rewritten cards still satisfy the card/chunk equality, and `chunk --dry-run` reports `chunked: 0`.

### Task 5: Live validation (owner approval required)

1. Dry run `rehash_content_hashes` against the live hub; review counts (expected: nothing "stale" that was not already stale; compare with the `index_card_stale` count from `corpus_health scan`).
2. Copy test: on a scratch copy of one course's cards and notes, convert all notes to the other line ending and confirm `rebuild --plan` reports 0 refresh.
3. With the owner's go-ahead and a quiet hub (no pipeline or other writer), run `--apply`, then rescan.
4. Only afterwards: the owner decides whether to add `.gitattributes` to `academic_notes` (renormalizing about 930 files; check tablet sync behavior first).

### Task 6: Docs

`core/indexer/README.md` hash section, `docs/trackers/academic_hub_to_do.md` (replace the line-endings follow-up), `CLAUDE.md` (drop the "hash is currently line-ending sensitive" caution once merged).

## Risks and open questions

- Mixed-ending files and lone `\r`: documented behavior above; a test pins it.
- `audio_generator/state.py`, `agent/rag/resolve_questions*.py`, `pipelines/*` import the hash functions; Task 3's audit decides whether any keeps its own stored hash that needs the same treatment.
- Hash version churn: this is the third scheme. If the owner wants to stop accumulating schemes, an alternative is a single versioned hash string (`v2:...`) in new cards. Not recommended now: it changes the stored format read by several tools.
- The 16-hex truncation is unchanged; collision risk is negligible at this corpus size.
