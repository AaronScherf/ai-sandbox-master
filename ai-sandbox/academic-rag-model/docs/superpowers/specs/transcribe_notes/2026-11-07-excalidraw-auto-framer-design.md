## Goal, requirements, and constraints

The user invokes one script on the active Excalidraw canvas to frame slide/explanation/handwriting groups for ordered PDF export. A normal pair has a 907 × 510 slide image and one rendered `markdown-image` explanation; either may also have nearby freehand annotations. The recovered 2SLS note has a regular two-lane layout, but this is not a universal coordinate grid. The script must preserve all content, respect existing manual frames, avoid duplicate frames on rerun, order pages by slide number where numbers are available, and report groups it cannot frame safely. Physical relocation of slide or handwriting elements is outside this framer's first release.

The brainstorming document reports 108 elements, including 30 frames, in `Econometrics 2026-10-28 2sls recovered.excalidraw.md`. These counts and its measured frame sizes are *reported observations*, not independently remeasured here. The source note lives in the separate `academic_notes` Git repository. The vault's installed Excalidraw plugin manifest reports version 2.29.1 and its configured script directory is `Excalidraw/Scripts`.

A read-only decode of `Econometrics 2026-11-04 LIML2 10.09.10.excalidraw.md` on 2026-11-08 found 2,570 `freedraw` elements, 48 images, and 24 rectangles; it contained no frame elements in that snapshot. Slide image positions span much wider x coordinates than the 2SLS grid. One sampled PNG visibly displays `18/56`, while its asset filename has an opaque suffix. These observations invalidate a hard-coded x = 950 lane split and show that slide order cannot be recovered from filenames or canvas y position alone. They do not establish that every slide has a legible number or that every ink region has a unique slide.

The plugin's [EA type declaration](https://github.com/zsviczian/obsidian-excalidraw-plugin/blob/master/docs/API/ExcalidrawAutomate.d.ts) confirms `getViewElements()`, `copyViewElementsToEAforEditing()`, `getElements()`, `addFrame()`, `addElementsToFrame()`, and `addElementsToView()`. `getElements()` exposes **workbench** elements, not the active scene. Editing immutable view objects directly is prohibited by that API. Confirm the installed plugin supports these methods before implementation. The installed `Excalidraw/Scripts/Downloaded/Printable Layout Wizard.md` says PDF page order is alphabetical by frame name, frames define print areas rather than content ownership, and same size/orientation is needed for a uniform PDF. Those claims still need a scratch export check in this vault.

|---|---|---|---|---|---|
| Scan | `ea.getViewElements()` on active note only; classify slide, explanation, freehand stroke, and existing frame | Read-only, local | Classified IDs, ink-region boxes, warnings | Repeatable | Compare varied source regions with canvas |

No scheduled execution, background scan, service, or persistent database is required. The slide-number map is a small per-scene input artifact or persisted image metadata, not a scan ledger. A no-op run creates no scene changes. User-facing review is the in-canvas preview/report; ambiguous associations are skipped. If a later workflow asks a human to make formal owner decisions, use the project's interactive Artifact convention rather than a raw JSON decision file.

## Discovery, pairing, and geometry

1. Read `ea.getViewElements()` and exclude deleted frames, decorative rectangles, and unrelated images. Identify slide candidates by `type=image`, 907 × 510 within a small rendering tolerance **or** 16:9 ratio plus an asset link to a slide PNG. Ratio alone is insufficient. Identify explanations by `type=image` and the plugin's `markdownImage` custom data or matching `## Embedded Files` registration. Treat `freedraw` as handwriting candidates, not as slides or explanations; a two-panel exercise may contain two explanations and no slide.
2. Build a verified order map `(deck identity, displayed slide number, source image element ID, asset fileId/hash)`. The page number is image content, not an Excalidraw field; an EA-only script has no established OCR capability. The subscription agent may read the PNGs once and provide a small number map, or the user may enter numbers in the preview. Do not infer a number from an opaque asset filename or canvas position. Reject duplicate `(deck, number)` keys unless they are explicitly recognized as repeated appearances. Missing numbers are reported and may be framed only when their order is explicitly supplied. A changed asset hash invalidates its number entry. Frame names use zero-padded global ordinals derived from `(deck, number, continuation part)`, independent of physical positions.
3. Pair slides and explanation images using **relative** geometry and existing associations: vertical overlap/center distance, horizontal separation, and unique nearest neighbor within a bounded local neighborhood. The old Δy ≤ 250 px row rule is a useful candidate generator for the regular 2SLS layout, not a universal gate. Infer local row bands from the actual slide boxes; do not split on an absolute x = 950. For the irregular LIML2 layout, require a unique explanation match or report `ambiguous_pair`. A slide can have zero or more handwriting regions and may have no explanation; do not force one-to-one ink ownership.
4. Group nearby `freedraw` strokes into bounded handwriting regions using stroke bounding boxes, gaps, and local density. Prevent a long connecting stroke from merging a whole page into one region. Associate each region by overlap or nearest boundary with one slide's local band, or with a **contiguous slide-number range** when it spans adjacent slides. Spatial association identifies print inclusion, not semantic meaning; no handwriting transcription is needed. Regions equidistant from unrelated slides, crossing noncontiguous slide groups, or lying outside safe bounds are `ambiguous_ink` and must be previewed as unverified ink. A strict-ink run skips a frame that cannot include them safely; the default run may frame its clear slide/explanation core while reporting the risk. Preserve every stroke's ID and coordinates. A frame may spatially include many strokes without assigning each stroke a `frameId`.
5. Compute the union box of slide and explanation for the core frame. A normal frame uses `W = max(Xmax − Xmin + 80, 1980)` and `H = clamp(Ymax − Ymin + 60, 570, 620)`. Set `frame.x = (Xmin + Xmax − W)/2` and `frame.y = (Ymin + Ymax − H)/2`. Balanced 40 px horizontal and 30 px vertical padding remain targets. Allow 750–850 px for taller content. Default best-effort mode first expands to the matched-ink union when that box fits and contains no other image; otherwise it retains the core frame and reports at-risk ink before apply. Optional `inkPolicy: "strict"` in the slide-order sidecar computes the larger content-and-ink box and skips if it does not fit. A 1840 × 800 exercise frame remains a later milestone.
6. Ensure planned frames do not overlap unrelated content or neighboring groups. If they do, report `geometry_conflict`; do not shift source elements. Use numbered frame names so Printable Layout Wizard's alphabetical PDF order follows the verified slide order even when the canvas is spatially scrambled. Mixed standard/tall dimensions need a scratch export check before promising one uniform PDF.

## Slide-order manifest and movement boundary

The script reads a vault-local sidecar beside the exact scene, named `<scene basename>.slide-order.json`, when numbered PDF ordering is requested. Each entry contains `slideElementId`, `fileId`, asset content SHA-1, `deck`, and the displayed integer `page`/`total` (if shown). An agent that has already viewed the PNGs can create this map without a new metered call; the framer validates the IDs and hashes against the current scene before using it. The sidecar is machine input, not an owner-decision ledger. If numbers are absent or conflicting, the script reports them in its preview and does not silently sort by coordinates or apply an order-dependent frame plan. For a handwriting region linked to two adjacent slide numbers, a single combined print area is allowed only if it encloses both slides and their ink without clipping; otherwise mark the region `shared_ink_needs_review`.

The first release changes **frame names/order and boundaries**, not the positions of slides, explanations, or strokes. This is sufficient to reorder PDF pages because the installed Printable Layout Wizard sorts frame names alphabetically. Physical canvas reflow needs a separate follow-on design: moving an image alone can sever its spatial connection to hundreds of strokes, and the script cannot infer that those strokes should move from slide numbers alone. A future reflow proposal must specify a validated group map, collision-free target layout, reversible preview, and all-writer coordination before it can mutate content coordinates.

## EA mutation and reruns

For an invocation, call `ea.getViewElements()` first. For each planned print group, derive a stable key from sorted **slide and explanation element IDs** plus panel part or slide-number range; associated ink IDs are audited but do not change the group's identity when a stroke is added. Search existing frames by their `frameId` member set, then by a managed marker in frame `customData` if that field survives save/reopen. Adopt an unmarked legacy frame only when membership is exact and its bounds are uniquely close to the planned group; this prevents the first run on a manually framed note from stacking a new frame on top. On multiple candidate frames or conflicting manual membership, leave the canvas unchanged for that group and report `ambiguous_existing_frame`.

Copy the affected existing frame and member elements with `ea.copyViewElementsToEAforEditing(elements, true)`; `ea.getElements()` then supplies editable copies. For a new frame call `ea.addFrame(x, y, width, height, name)`. For an adopted or managed frame edit its copied `x/y/width/height/name` under the **same ID**. Call `ea.addElementsToFrame(frameId, memberIds)` for each new or changed membership when scene grouping is desired, and check that members no longer retain an obsolete `frameId`. This membership is not a prerequisite for Printable Layout Wizard PDF inclusion: it uses the frame's spatial print area. Await one `ea.addElementsToView(false, true)` after planning all changes. Clear the EA workbench afterward. Never use `cloneElement` to update an existing frame: it creates another ID.

A second run on an unchanged scene must produce zero new frames and zero changed element versions. If source positions or sizes change, update the same managed frame ID. If a source member disappears, report its frame as stale and leave it untouched pending review; do not delete a user frame automatically. The managed marker's exact field and plugin save behavior are implementation prerequisites, tested on a scratch copy. A failed commit must surface as a failed run, not as a success message.

## Acceptance and verification plan

- On a **scratch copy** of `Econometrics 2026-10-28 2sls recovered.excalidraw.md`, inventory elements and manually compare a varied sample: normal pair in each lane, tall slide 22 and 23, and exercises 1–4. On a separate copy of finished LIML2, sample numbered slides moved out of spatial order, dense ink beside a slide, ink spanning adjacent slides, and unrelated strokes. Record false positives before trusting total frame counts.
- First run shows each planned group, verified deck/page order, ink-region assignment, at-risk ink count, adoption/new-frame decision, bounds, and skips. A deliberately shuffled pair exports in slide-number order without moving source elements. Missing/duplicate numbers block apply; ambiguous ink is disclosed. Normal frames satisfy the width formula and 570–620 px height for slide/explanation content; taller core content fits 750–850 px or is blocked. No slide or explanation is clipped. In best-effort mode, any possible handwriting omission is conspicuous in the preview and result; strict mode blocks it.
- Save and reopen. Frame IDs, names, and member `frameId` links persist. A second run changes no IDs or bounds; moving one explanation adjusts only its matched frame. An ambiguous existing frame produces a skip without mutation.
- Export the scratch copy to PDF and compare every page against the verified deck/page sequence, continuation order, handwriting inclusion, and legibility. A successful frame fixture test alone is not evidence that PDF export order works.

**Release boundary:** The smallest useful release frames unambiguous normal groups with confident ink association and verified slide-number ordering; it reports every unresolved group. Adaptive framing and two-part exercise support can follow after scratch-canvas validation. Physical canvas reflow is separate. No server, database, or automated launcher is needed. Remaining validation gates: whether the installed plugin preserves a managed `customData` frame marker, whether the order sidecar can be read in-vault, and how mixed frame sizes behave in the installed PDF exporter.
